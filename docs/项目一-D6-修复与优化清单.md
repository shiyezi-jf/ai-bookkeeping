## 二、P0 · 必须修复

### R1 · 超支提示文案把"预算金额"写成了"超出金额"

**修改位置**

`frontend/src/views/Home.vue` 第 367–369 行，预算提示的 `v-if="stats.budget.exceeded"` 分支。

**现状代码**

```vue
<span v-if="stats.budget.exceeded">
  本月已支出 ¥{{ stats.budget.spent }}，已超出预算 ¥{{ stats.budget.amount }}
</span>
```

**修改内容**

```vue
<span v-if="stats.budget.exceeded">
  本月预算 ¥{{ stats.budget.amount }}，已支出 ¥{{ stats.budget.spent }}，已超支
</span>
```

**修改原因**

1. `stats.budget.amount` 是后端返回的**预算额度**，不是超出的差额。"已超出预算 ¥3000.00"会被读成"超了 3000 元"。
2. 按 D6 §6.3 验收第 6 步把预算临时改为 `1` 元时，现文案会显示"已支出 ¥578.00，已超出预算 ¥1.00"，验收时极易被自己的提示误导。
3. 新文案不在前端做 `spent - amount` 的减法，符合"前端不做金额计算、聚合全在后端"的质量要求。

**预期效果**

- 超支时提示为：`本月预算 ¥1.00，已支出 ¥578.00，已超支`。
- 红色语义样式（`.budget.exceeded`）不变。
- 未超支时的中性提示（`本月预算 ¥3000.00，已支出 ¥578.00`）保持不变，符合文档"无提示或中性提示，二选一并固定"。

**验证方式**

1. 修改 `budgets` 表本月总预算为 `1.00`（见第五节命令）。
2. 刷新页面，确认出现红色提示且文案与上面一致。
3. 恢复预算为 `3000.00`，确认红色提示消失、中性提示恢复。

## 三、P1 · 建议修复

### R2 · 饼图 tooltip 金额没有统一两位小数

**修改位置**

`frontend/src/components/StatsCharts.vue` 第 36–39 行，`pieOption()` 中的 `tooltip.formatter`。

**现状代码**

```ts
tooltip: {
  trigger: 'item',
  formatter: '{b}<br/>¥{c}（{d}%）',
},
```

**修改内容**

```ts
tooltip: {
  trigger: 'item',
  // 与折线图 tooltip 保持同一种写法：先收窄类型，再格式化
  formatter: (params: unknown) => {
    const p = params as { name: string; value: number; percent: number }
    return `${p.name}<br/>¥${Number(p.value).toFixed(2)}（${p.percent}%）`
  },
},
```

**修改原因**

1. `{c}` 输出的是原始数值，如 `238`，与列表、预算提示里的 `238.00` 显示口径不一致。
2. 项目全程金额统一两位小数，图表是唯一的例外，验收截图时会被注意到。
3. 采用与 `lineOption()` 相同的 `unknown + 收窄` 写法，避免引入 `any`。

**预期效果**

- 悬浮任一扇区显示：`餐饮 ¥238.00（41.2%）`。
- 金额格式与页面其他位置一致，且不参与任何账务运算。

**验证方式**

依次悬浮 2–3 个扇区，确认金额均为两位小数，占比数值正常。

### R3 · `month` 单数字格式被放行（如 `2026-1`）

**修改位置**

`backend/app/periods.py` 第 6–21 行，`month_range()`。

**现状代码**

```python
def month_range(month: str) -> tuple[date, date]:
    try:
        years_s, mons_s = month.split("-")
        year = int(years_s)
        mon = int(mons_s)
        ...
```

**修改内容**

```python
def month_range(month: str) -> tuple[date, date]:
    # 契约要求严格 YYYY-MM：先卡长度和分隔符位置，再交给 date() 校验数值合法性
    if len(month) != 7 or month[4] != "-":
        raise HTTPException(status_code=400, detail="month 格式必须为 YYYY-MM")

    try:
        year = int(month[:4])
        mon = int(month[5:])
        ...
```

**修改原因**

1. D6 §4.2 约定 `month` 格式为 `YYYY-MM`，非法格式返回 400；但 `int("1")` 能成功，导致 `2026-1` 返回 200。
2. 同一份校验被列表与统计接口共用，放行单数字月份会让两个接口的入参边界不一致地"宽松"。
3. 先卡格式再 `date()`，`2026-0`、`2026-13`、`abc` 等仍会正确落到 400，逻辑不重复。

**预期效果**

- `GET /api/stats/monthly?month=2026-1` 返回 400。
- `GET /api/transactions?month=2026-1` 返回 400。
- 前端 `value-format="YYYY-MM"` 始终发送两位月份，正常使用不受影响。

**验证方式**

```powershell
# 期望 400
Invoke-WebRequest "http://127.0.0.1:8000/api/stats/monthly?month=2026-1"
# 期望 200，trend 为 2025-08 ~ 2026-01
Invoke-WebRequest "http://127.0.0.1:8000/api/stats/monthly?month=2026-01"
```

## 四、P2 · 可选优化

### O1 · 去掉 `watch` 上多余的 `deep: true`

**修改位置**

`frontend/src/components/StatsCharts.vue` 第 151–152 行。

**现状代码**

```ts
watch(() => props.stats, render, { deep: true })
watch(() => props.categories, render, { deep: true })
```

**修改内容**

```ts
// Home.vue 每次都是整体赋值（stats.value = ...），引用必然变化，浅监听即可
watch(() => props.stats, render)
watch(() => props.categories, render)
```

**修改原因**

父组件所有更新都是整体替换对象/数组，`deep` 不会带来额外触发，反而会递归遍历整棵对象树（`trend` 6 条、`summary` 最多 8 条，规模不大但属无意义开销）。只有在"原地修改属性"的场景才需要 `deep`。

**预期效果**

- 切月、新增、编辑、删除后图表仍正常重绘。
- 去掉无意义的深度遍历，代码意图更明确。

**验证方式**

切月一次、编辑一条金额保存一次，确认两张图都立即变化。

### O2 · 明确"趋势全为 0"的口径（二选一，需决策）

**修改位置**

`frontend/src/components/StatsCharts.vue` 第 30–32 行，`hasTrend`。

**现状代码**

```ts
/** 6 个月全为 0 时折线是一条贴底的直线，没有信息量，按空状态处理 */
const hasTrend = computed(() => trend.value.some((t) => Number(t.amount) > 0))
```

**方案 A（推荐，保持现状，只补注释口径）**

不改逻辑，仅在验收/README 中说明：`trend` 契约恒为 6 条，但金额全为 0 时按"无数据"处理，展示空状态文案。

理由：

- D6 §6.4 要求"图表无数据时展示空状态文案"；6 个月全 0 等价于"没有任何记录"。
- 与饼图的空状态判断（`summary.length === 0`）在用户视角上一致：没记过账就显示文案。

**方案 B（改为保留贴底直线）**

```ts
const hasTrend = computed(() => trend.value.length > 0)
```

理由：能直观证明"后端补零骨架生效"，且空月份本身就是信息。

**修改原因**

这不是 bug，而是产品口径问题。两种都能通过功能验收，但必须能解释自己的选择（面试会问"为什么趋势要补零"，紧接着就可能问"全 0 时为什么这么处理"）。

**预期效果**

无论选哪种，口径写进注释或 README，验收与后续维护不再摇摆。

## 五、N · 本轮不处理（记录项）

- **位置**：`frontend/src/components/StatsCharts.vue` 第 3 行 `import * as echarts from 'echarts'`。
- **现状**：`npm run build` 产物 `index-*.js` 约 2.19 MB（gzip 约 720 KB），触发 Vite 的 chunk 体积警告。
- **结论**：D6 §6.3 明确"本轮以能跑通、可读为准"，全量引入可接受。
- **后续**：D7 部署时再评估按需引入（`echarts/core` + `PieChart` + `LineChart` + `GridComponent` / `TooltipComponent` / `LegendComponent` + `CanvasRenderer`），届时需回归两张图。

### N2 · 快速切月的请求竞态

- **位置**：`frontend/src/views/Home.vue` 的 `fetchStats()`。
- **风险**：连续快速切换月份时，先发出的请求可能后到达并覆盖新月份的数据。
- **结论**：不属于 D6 验收项，本轮不改。
- **后续方案（若做）**：在 `fetchStats` 内维护递增序号，请求返回后比对，不一致就丢弃；不要用 `AbortController` 之外的额外状态污染列表逻辑。

### N3 · 预算只在启动时播种（文档要求写入 README）

- **位置**：`backend/app/main.py` 的 `lifespan` 播种逻辑。
- **要求**：D6 §4.3 明确"预算只在应用启动时播种，跨月长期运行需重启"这一限制**必须写入 README**。
- **待确认**：检查 README 是否已补该说明，未补则补一段"已知限制"。

# D4 · 录入页 + 预览确认 + 列表：任务清单

> 目标：浏览器里完成「输入一句话 → 核对/修改 → 确认 → 列表多一条」的完整闭环。
> 改动范围：只改 `frontend/src/views/Home.vue`。`api/index.ts` 已够用，不需要动。

---

## 0. 前置共识

### 0.1 接口契约（已就绪，照着用）

| 接口 | 请求体 | 响应 |
|---|---|---|
| `POST /api/parse` | `{ text }` | `{ draft, fallback, message }` |
| `POST /api/transactions` | `{ amount, category, occurred_on, note?, raw_text?, source? }` | 201 + 一条账单 |
| `GET /api/transactions` | 无 | 账单数组（按日期倒序） |

### 0.2 一条必须知道的细节

后端的 `amount` 是 `Decimal`，序列化成 JSON 后是**字符串**（如 `"35.00"`）。
前端全程当字符串处理，**不要 `parseFloat`，也不要 `toFixed`**——否则等于把精度问题从后端搬到前端。

### 0.3 三层宽严的落点

- `TransactionDraft`：字段可空（模型可能没识别到）；
- `TransactionCreate`：金额、分类、日期必填；
- **前端**：负责在"用户能看懂的地方"把空值补上。

所以「确认按钮什么时候可点」不是体验问题，是**数据正确性问题**。

## 第 ③ 步：把只读卡片改成可编辑表单

### 现状

`Home.vue` 里的 `<dl class="draft">` 是只读展示（`<dd>` 只能看，不能改）。

### 任务 1：新增 `form` 对象

```ts
const form = ref({ amount: '', category: '', occurred_on: '', note: '' })
```

**为什么不用 `draft` 直接绑输入框：**

- `draft` = 模型的原始答案（保留作证据）；
- `form` = 用户改完的答案（真正提交的东西）。

分开之后，以后才能统计"模型错了几次、用户改了哪些字段"，也能做到"重新解析不覆盖用户已改的内容"。

### 任务 2：解析成功后，把 `draft` 拷进 `form`

在 `handleParse` 拿到 `res.draft` 之后加一段：

| 字段 | 转换规则 |
|---|---|
| `amount` | `null` → `''` |
| `category` | `null` → `''` |
| `occurred_on` | `null` → **今天**（不是空） |
| `note` | `null` → `''` |

### 任务 3：新增分类常量

```ts
const CATEGORIES = ['餐饮', '交通', '购物', '居住', '娱乐', '医疗', '学习', '其他']
```

下拉框用它渲染，不要手写 8 个 `<option>`。

### 任务 4：把 `<dd>` 换成输入控件

| 字段 | 控件 | 必须带的属性 |
|---|---|---|
| 金额 | `<input>` | `type="number"` `step="0.01"` `min="0.01"` `v-model="form.amount"` |
| 分类 | `<select>` | `v-model="form.category"`，第一个 option 为 `value=""`（请选择） |
| 日期 | `<input>` | `type="date"` `v-model="form.occurred_on"` |
| 备注 | `<input>` | `maxlength="200"` `v-model="form.note"` |
| 置信度 | 不动 | 继续只读显示 |

**注意：金额不要用 `v-model.number`**，否则 `"12.80"` 会变成 JS number `12.8`。

### ③ 自测标准

- [ ] 解析「昨天打车35块」→ 金额 35、分类"交通"、日期 11-09、备注有值；
- [ ] 解析「工资到账8000」→ 分类为"请选择"、日期为今天，页面不报错；
- [ ] 四个框都能手动修改，页面不崩。

## 第 ④ 步：确认按钮 + 列表

### 任务 1：新增 4 个状态

| 变量 | 作用 |
|---|---|
| `submitting` | 提交中，防止连点重复入库 |
| `list` | 账单数组 |
| `listLoading` | 列表加载中 |
| `submitError` | 提交失败提示（与解析的 `error` 分开） |

**为什么要分开两个错误提示**：解析失败和保存失败是两件事，分开展示，用户才知道该重试哪一步。

### 任务 2：新增 `canSubmit` 计算属性

三个条件同时满足才允许提交：

1. `form.amount` 非空且大于 0；
2. `form.category` 非空；
3. `!submitting`。

### 任务 3：写 `handleSubmit`（顺序固定，不能换）

```
1. submitting = true
2. await createTransaction(payload)
3. 成功：清空 form / draft / 输入框
4. await fetchList()
5. finally: submitting = false
```

**payload 拼装（4 个坑）：**

| 字段 | 取值 |
|---|---|
| `amount` | `form.amount` 原样字符串，**不要转数字** |
| `category` | `form.category` |
| `occurred_on` | `form.occurred_on` |
| `note` | 空字符串 → `null`（空字符串和"没填"是两件事） |
| `raw_text` | 当初输入的那句话 `text.value` |
| `source` | `fallback ? 'manual' : 'llm'` |

**为什么传 `raw_text`**：它把"AI 看到的话"和"入库的结果"绑在一起。D6 做统计、面试时讲"每条数据可追溯到原始输入"，靠的就是它。

### 任务 4：写 `fetchList` + 首次加载

- `fetchList`：用 `listLoading` 包住 `listTransactions()`，结果赋给 `list`；
- 组件挂载时（`onMounted`）调用一次。

### 任务 5：模板加两块

1. **确认按钮**：放在卡片里，`:disabled="!canSubmit"`；
   当 `canSubmit` 为 false 时，按钮下方显示原因（如"请先填写金额和分类"、"提交中…"）。
2. **列表区块**：放在页面最下方，遍历 `list` 显示 日期 / 分类 / 金额 / 备注；
   `list` 为空时显示"还没有记录"（不要留一片白，空白页会让人以为坏了）。

### ④ 自测标准

- [ ] 「昨天打车35块」→ 改一下备注 → 点确认 → 列表立刻多一条，内容与改后一致；
- [ ] 「工资到账8000」→ 确认按钮是灰的，且有提示；
- [ ] 后端停掉 → 点确认 → 有错误提示，**表单内容还在**；
- [ ] 连点确认 5 次 → 列表只多 1 条。

第 4 条是这步真正的关卡：防重复不是体验问题，是**会往数据库里塞脏数据**的问题。

## 附：三个高频坑

### 坑 1：日期默认今天，别用 `toISOString()`

`new Date().toISOString().slice(0, 10)` 取的是 **UTC 日期**。在东八区，早上 8 点前打开页面会得到"昨天"。

`<input type="date">` 需要 `YYYY-MM-DD`，请用 `getFullYear()` / `getMonth() + 1` / `getDate()` 自己拼，并给月份和日期补零。

### 坑 2：`await` 顺序错 = 列表不更新

必须 `await createTransaction(...)` 成功之后，再 `await fetchList()`。
先刷新后保存，看到的一定是旧列表——这就是手册里那条"点确认后列表没刷新"的预案。

### 坑 3：失败时不要清空用户输入

请求失败就把用户填的内容清掉，是最伤人的交互。
清空只发生在**成功之后**；`catch` 里只写错误提示。
